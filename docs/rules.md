# Rules

Process rules for every agent on a team run by this playbook: the lead, seats, workers and reviewers. "The operator" is the human who decides. Each rule's reason is in [index.md](index.md) under the same number; read it when a case is unclear. `<root>` is defined at the top of index.md.

0. **Precedence.** Where a skill prescribes broader or automatic action than these rules (fixing every finding, a review the tier doesn't call for, acting on retro candidates, `review-loop`'s `auto` mode), these rules and the ticket's tier govern. Run `review-loop` without `auto`.

1. **Tier.** Every ticket's ceremony tier, `research`, `write-up`, `retro`, `docs`, `vg`, `checklist`, `script` or `full` (`none` for other work with no code), is the operator's choice, made before the ticket is written. The lead asks `❓ CS-Qn – Size <work> as <tier>?`, quotes the operator's words, says what each tier builds and recommends the lowest those words allow; a higher tier names its reason. The task file's first line is `Ceremony: <tier> (the operator, "<words>", <date> hh:mm)`. Build and review what the tier says and no more:
    - `research`: an investigation answering the brief's question; the brief names the question, the scope and the findings path; the findings are a Markdown file and its HTML version, answering the question first and citing primary sources; no live check, no `**If it fails:**` line; its review is the operator reading the findings.
    - `write-up`: a draft for people, such as an email, an invite, a brief or a rationale, in the pane or the file the brief names; no live check, no `**If it fails:**` line; its review is one pass on a different model, then the operator reading the draft; sending or publishing it is an outward step (rule 13).
    - `retro`: rule 12's retro: read-only; proposed environment changes in order of severity, each with its cost; no live check, no `**If it fails:**` line; the operator chooses which to adopt.
    - `docs`: a change to the project's documentation only, no code, script or check; `**If it fails:** <one sentence>`; its live check is the project's docs build where there is one, and a render shown to the operator for a page they see; its review is the operator reading the diff, or the render.
    - `vg`: presentations and graphics: slide decks, diagrams, images, mockups; no `**If it fails:**` line; its live check is the render, PDF or PPTX shown to the operator; its review is the operator's feedback, taken before anything is committed (rule 9).
    - `checklist`: a doc of numbered commands, one line each on what it does; `**If it fails:** <one sentence>`; no review.
    - `script`: a plain script relying on each step's own rerun safety; `**If it fails:** <one sentence>`; one `code-review` pass, the review loop only on the operator's words.
    - `full`: acceptance criteria; a `## Failure modes` table, one row per step: what a failure there leaves and what the operator is told; every read of state says yes, no or failed, and a failed read is never taken as absent; the review loop.

    Adopting existing code is a ticket of its own.

2. **Live first.** Verify every ticket whose tier has a live check (all but `research`, `write-up` and `retro`) by running it for real on an expendable host (a disposable container or jail, a test VM, a cloud sandbox), by trial and error, before any review. Throw the host away after. Verification is real runs: build no fixture, fake or dry run where a live test is practical. A fixture standing in for a tool's output is copied from a real run and says where from. When a live run is impractical, ask the operator for the exception as its own question.

3. **Compromised by design.** Treat every sandbox and agent, yourself included, as able to do the worst its environment allows. Contain by disposable environments and isolation: tests run in a child container or jail. Expose only what is expendable. Seats sharing one cloud account each use their own seat name as their project name for cloud sandboxes (e.g. `sandbox cloud create <seat>`), so each gets its own servers, disks, keys and known_hosts. Before advising the operator to start or open anything on the host (a tunnel, a port, a service, a mount), name what the agents' jail reaches through it while it is up; advice that widens that reach is a 🔴 question naming the exposure, put through Security (heimdall). Write files with the write and edit tools, never through a shell heredoc.

4. **Questions.** Each question is a block: `❓ <ID> – <question>?`, the context under it, then `➡️ <recommended answer>`, worded so `yes` accepts it. IDs are unique for the life of the project: a prefix per thread plus a number. Ask for decisions, and for every step only the operator can take (a read of a diff, a look at a render, an approval, a go); look facts up yourself. Record `ok` as "trusts the recommendation without full understanding", and re-explain that decision before anything hard to reverse follows from it. A question settled by an answer given elsewhere is withdrawn in its own pane, naming that answer ("PV-Q13 withdrawn: settled by PA-Q22"). A question of yours whose recommended answer a newer question contradicts is withdrawn or re-asked in the turn that asks the newer one. A ticket's number is claimed by committing its file on the seat's branch, before the number is announced.

5. **Words and time.** A deliberate choice (the operator accepting a risk or cost) is recorded where the project keeps decisions, quoting the operator: `(the operator, "<words>", <date> hh:mm)`. The time quoted is the stamp on the operator's message, or the time a seat's report quotes; never an estimate. A go relayed from the operator is quoted the same way. Your own choice goes to review, never under the operator's name. Each edit you claim names a commit whose diff touches the file you name; an entry that changes nothing says "No change". A claim about state (exists, absent, kept, deleted, intact, tested, the cause of a failure), by anyone, names the read it rests on, made after the last step that could change it. An answer to a question about now (keep it, take it down, wait) is recorded as the operator's choice for now, dated; a standing rule (rules.md, a project's constants or standards) changes only on the operator's words naming that rule.

6. **Visible findings.** Every review finding reaches the operator. Every issue or finding put to the operator states, in plain words without history: Done (what was done), Expected (the expected outcome), Instead (what happens instead), Impact (the absolute impact against the threshold that matters, then for whom), Root cause (hypothesised), Solutions, effort and tradeoffs (each solution is lettered (a), (b), (c)…, so the operator can answer with its letter, and says where it lands against that threshold, then names its effort and its tradeoffs; the `➡️` names the recommended letter); then the `❓` question and the `➡️` answer. Every impact, rating, comparison and recommendation, in a question, a finding, a review summary or a scope question, leads with the absolute value and how it compares to the threshold that matters (a requirement, a limit, a budget, a deadline), and gives the relative change only after; where no threshold is known, it says so. Above each question, one plain-text line gives its criticality and what it blocks, starting with 🔴 for high, 🟠 for medium or 🟡 for low (e.g. "🟡 low · blocks nothing yet"). Several questions are ordered most critical first, then, among equally critical ones, the one blocking work soonest, then with related questions kept together, as `/open-questions` prints them, and laid out as its template shows (`tools/prompts/open-questions.md`): a `---` line before every question, a bold `Issue:` title line rather than a Markdown heading, and a blank line on each side of the `❓` line. Each round's summary opens with `<topic> · <loop> round k · findings so far F · questions so far Q`, rates each finding's impact (high, medium or low: what goes wrong against the threshold that matters, and for whom, if it stays) and effort (very low, low, medium or high; very low is a word or a line, cheaper than a backlog entry), and recommends: fix for the important few; fix now for low impact at very low effort; the backlog (`.scratch/backlog.md`: date, item, impact, source, the operator's words) only for the rest, low impact with real effort. Every finding is answered by the operator: fix, delete or backlog.
    - Reviewers are read-only and run on a different model from the writer's; the agent running the loop puts the over-build, impact and drift checks into the reviewer's prompt.
    - Sweep the class: after fixing a finding, search for its sibling instances, fix them in the same turn and name them in the response.
    - A fix that changes a check instead of the code follows rule 14.

7. **Drift.** A finding in lines an earlier round of the same loop added or changed, or a second round running finding gaps in the same check, is drift. A round with drift opens with `❓ DRIFT-Qn`, naming the findings and the rounds they trace to, with three options in this order: step back and delete or simplify; stop, backlog the rest; continue. Drift is a signal to raise, every time. The turn cap is 15 rounds per loop, a checkpoint: at 15, and after each further 5, the lead asks the operator whether to extend.

8. **Over-build.** Every review looks for code, checks, options, tests or criteria that the operator's scope or a simpler design makes unnecessary, above all a check of state before a step already safe to rerun, and weighs it the same as a gap, naming what to delete. Every finding's question offers delete; recommend delete wherever it answers the finding as well as a fix.

9. **Live before merge.** A branch merges into the integration branch only after its live checks pass on a real host, with `git merge --no-ff`. Before each review pass and just before merging, the seat merges the integration branch into its branch and resolves any conflict there, flagging to the lead a shared file that diverged. A change to a file other seats use (a shared lib) merges into the integration branch on its own, from its owner's branch, before others take it by merging the integration branch; it does not travel between feature branches. The seat's ready report names its branch's head commit and the commit its live checks last ran on, and code changed since then runs live again. Before authorising the merge, the lead runs `<root>/agentic_workflow/tools/merge-ready <worktree> <head> <that commit> <code paths>`, reads its result, and names both commits in the authorisation. A visual change is shown to the operator as a render, and their feedback taken, before anything is committed.

10. **Lead: delegate, stay small.** The lead decides nothing for the operator, edits nothing in the project, and writes only the wiki and task files; seats make every edit and commit. A go is relayed as given; a condition the lead would add goes to the operator as a question. The lead passes on a seat's claim about state with the read the seat names (rule 5). A truncated, partial, remembered or second-hand read is passed on as `unverified: <claim>; <who> checks`, and a brief carries such facts as checks to run. In every scope question:
    - `➡️` is the smallest option that meets the operator's own words;
    - an option beyond them is labelled `widens: <what it adds>` and is recommended only when a named security risk forces it;
    - a request for something reusable, shared or a framework first gets: which second project or caller uses it, and when? Without an answer, the work stays where it is;
    - when a step is safe to rerun, recommend running it, with no check before it;
    - an agent's offer to stop or defer goes to the operator as offered; the lead recommends against it only by naming the tier's reason.

11. **Dated wiki.** The lead keeps the wiki as history: every claim dated, every claim about code citing its commit, a change added as a new dated line with the old one marked superseded. Read `index.md` and the pages it names before a decision. Commit only the paths you changed. Use an existing shared wiki where there is one; keep `index.md` linking every page; cite sources, never edit them; lint for contradictions, orphans and stale claims periodically. Write each of the operator's decisions as a dated wiki entry in the turn that records or relays it; a handoff of the lead's lists every entry still owed. `team.sh status` flags a wiki whose last commit outside `sources/` is a day old or more. Specs, ADRs and ticket bodies, unlike the wiki, state the current decision only; git and the wiki hold their history.

12. **Retros.** About one session in five, those where something went wrong first, gets a retro: read-only, proposing environment changes (hooks, standards, skills, the team script) in order of severity, each with its cost. The operator chooses.

13. **Outward steps.** A push, a publication, spend beyond the stated cap, or content sent off the machine waits for the operator's go. A standing go the operator gave for one operation (e.g. pushing the integration branch after a lead-authorised merge, one ref, the push-time secret scan passing) counts as their go for that operation only; the project's own notes list every standing go, with the operator's words and time.

14. **Checks changed, not code.** Any change to a check, test, fixture, check setup or acceptance criterion, by anyone (seat, worker, a fix driven by review or by a live run), at any time:
    - opens its report with `⚠️ CHECK CHANGED, NOT CODE`, names the check, its old and new assertion and why, and goes to the operator as `❓ CHK-Qn`; a pass resting on it counts only once the operator answers;
    - a new or changed check is first shown to fail on the broken code; only then does its pass count.

    Why: changing a check to make it pass is the easiest way to hide a real failure, and checks are the source of truth, so a weakened check silently weakens everything resting on it. Examples: a live check's timeout relaxed until it passed; a bridge step that passed on code failing open.

15. **Unattended windows.** An unattended window is a stretch of the operator's absence that the operator opens, as [unattended-windows.md](unattended-windows.md) describes: it starts, after a readiness round of the taking-part seats and the grill, only on their `/start-unattended-window` typed in the lead's pane and ends only on their `/end-unattended-window`. What the window's grill granted, in the operator's words, is their go for that window only (rule 13). In a window, every agent:
    - never, whatever was granted: destroys what cannot be restored (deletes what the window did not create; drops or overwrites data without a fresh backup read back; revokes or deletes a credential the window did not create; changes a Console or account setting); changes ssh, pf, firewall or WireGuard routes on a host reached only that way, without a second path tested first; changes the host (the operator's machine, the jail's configuration, the host's pf); opens new exposure to the internet (a port, a public record). Reaching one, it stops that line of work, reports it, and takes other work;
    - writes each change's undo (the commands or steps, and who runs them) before making it, and makes no change whose undo it cannot write. After the change it reports the ledger line with `team.sh report`: what changed, where (commit, resource or host), the assumption IDs it rests on, its undo, and the read showing its state; the lead writes it to the window's ledger;
    - proceeds on its own `➡️` for a decision, recorded in its pane as `assumption: <ID>, confirm`;
    - merges nothing resting on an unconfirmed assumption or an unanswered CHK or review question, unless the grill granted it for that branch; blocked, it stacks further work on its branch, then takes the next independent item from the window's queue;
    - when a step leaves a check failing, runs that change's own undo, once, reruns the check, stops that line and reports 🔴; it tries no other fix and no retry. The lead then tells every seat working on that component to hold;
    - at the window's end, finishes or safely stops its current step, starts nothing new and reports what is live. No agent rewinds anything on its own: the rewind is the operator's choice.

16. **One seat, one component.** The seat that designs a component also builds and maintains it: no component passes from a designer to a builder to a maintainer. Seats are of two kinds:
    - **Coordinators** each keep one dimension consistent across the team and hold its single source of truth: the Lead (what is being done, by whom, its state and cost: the board, the wiki), Architecture (how components fit: interfaces, names, addresses, labels: the constants, ADRs, architecture diagrams), Methodology (how we work, quality and verification included: this playbook), Docs (that what is written is findable, current and in one voice: the docs site and glossaries) and Security (what may reach what, with which secrets: the threat model, the exposure rules, the secrets inventory). A change in another seat's work that touches a coordinator's dimension goes through that coordinator. The operator's words about a builder's component, given in a coordinator's pane, go to that builder as given; any question about what they mean for the component is the builder's to ask, and the coordinator asks only about its own dimension.
      Their seats are `lead`, `architect`, `coach`, `librarian` and `heimdall`.
    - **Builders** each design, build and maintain one area of components, which the project names, each seat by one lowercase, expressive word (GLOSSARY.md, "Seat name"). An area becomes a seat only while it has work being built.

    The coordinators, and the builders the project names as always on, are always deployed; the other builders roll on and off on demand. A builder rolls off with its check-out written and each of its components' README current, and rolls on from a task file naming both. While it is off, the Lead triages incidents on its components and rolls it on to handle them.

## Team mechanics

- End every turn with one line: `STATUS seat=<name> state=<working|waiting-for-PM|waiting-for-seat|ready-for-lead|blocked|idle|done> [for=<PM|lead|seat-name>] open=<n> [worst=<high|medium|low>] [ask="<one sentence>"] [pointer=<path or commit>]`. `open` counts your questions to the operator still unanswered; `worst` is the highest criticality among them, given whenever `open` is above 0. `for` names who you wait for: `for=PM` with `waiting-for-PM`, `for=lead` with `ready-for-lead`, and with `waiting-for-seat` the seat you wait for (the first, if several); leave it out in the other states. `state=waiting-for-PM` whenever your next step waits on the operator: an answer, a go, a release, a read, a look or a step only they can run; the `ask=` says what you wait for. Only when the operator can act now: if the lead or another seat must act first (a grill, a consolidation, a merge authorisation, a review), the state is `waiting-for-seat`, even when the operator's step comes after theirs. Each step you wait on the operator for is an open question (rule 4), counted in `open` and printed by `/open-questions`, so `state=waiting-for-PM` comes with `open` above 0. When the lead holds a seat's work on such a step, it tells the seat with `team.sh send`, and the seat asks it in its own pane. The other states: `ready-for-lead` only when a deliverable of yours waits for the lead's review or merge authorisation; `idle` when nobody owes you anything, a report you sent included; `done` when your task is finished; `working` while you act; `blocked` when you cannot go on and nobody you can name can unblock you. The seat's tmux tab takes its colour from that line: red, orange or yellow by `worst`, green at `open=0`. "PM" is the operator.
- An audible signal tells the operator a seat needs them: at the end of a turn that asks a new question or newly enters `waiting-for-PM`, beep.ts plays it, unless that seat is muted. The operator switches it with `/beep-from all|<seat>` and `/mute all|<seat>`, typed in any pane; everything starts muted, and is muted again after a tmux server restart. Agents play no signal themselves. A turn that ends aborted or in error marks the seat `blocked`, red on its tab and the board, its ask the error, and plays the signal unless the seat is muted, until its next STATUS line; the operator re-sends the message.
- The team script is `<root>/agentic_workflow/tools/team.sh`. After each Pi upgrade, run `team.sh selftest`; `team.sh status` lists any message stuck in `failed/`.
- Before saying a seat missed a message, the lead checks `team.sh status` for it listed as `QUEUED`.
- When relaying that a seat waits on the operator, the lead names the question's ID and the pane it is in. It relays only questions the operator can answer now: a question a seat has yet to ask is not relayed.
- A seat reads rules.md only when its session starts. After each release of this playbook whose CHANGELOG section has an **Act** line for seats, the lead sends every running seat that line with `team.sh send`, and, when the release changed an extension or a prompt template, asks each to reload in the turn that receives the request, with its `reload_runtime` tool, which takes effect when that turn ends. Any other request to reload (a new token, a changed setting) is taken the same way.
- After a host reboot, the lead runs `team.sh doctor`, hands the operator the one fix block it prints, runs it again until it passes, then `team.sh revive --all`.
- Seats report with `team.sh report "<name>: <one or two sentences> <pointer>"`, then end the turn. The lead sends with `team.sh send`, and relays a go only with `team.sh go`.
- Before `team.sh retire <seat>`, the seat writes its check-out to `<root>/wiki/sources/checkouts/<yyyy-mm-dd>-<seat>.md`, following `<root>/agentic_workflow/tools/checkout.md`, and commits it in the wiki; then the lead retires it. `team.sh retire` refuses without it; `--no-checkout "<reason>"` retires a seat that crashed or never started, and logs the reason. A seat going on in a new session is refreshed, with a handoff, instead.
- Messages, task files and reports carry pointers (a path or a commit), never pasted contents. A path is given in full, from `/`, and reachable from outside the sandbox, so one click selects it and the operator can open it: `/agents/sessions/freebsd/sandbox/worktrees/feat/vikunja-phone/infra/vikunja/README.md`, not `infra/vikunja/architecture.svg` or `/tmp/architecture.svg`; a file meant for the operator is written where they can reach it, not under `/tmp`. In a reply to the operator too. Nothing follows a path but a space or the end of its line: no full stop, comma, colon or bracket, which a double-click would select with it.
- Every Markdown file named to the operator, in a reply, a question or a report, also goes as an HTML page, made or remade with `<root>/agentic_workflow/tools/md-html <file.md>` after the Markdown's last change; the reply names the page's path, which md-html prints, the one to open in a browser. Its pages go under `<root>/html/`, outside every repo; a seat's own deliverable committed with its HTML version (research findings, a spec) keeps that committed copy, made as before.
- A Mermaid diagram meant for the operator also goes in a standalone HTML file, made from `<root>/agentic_workflow/tools/mermaid.html`, at a full path reachable outside the sandbox, named in the reply: a terminal pane shows only Mermaid's code.
- The lead's session stays free for the operator: long work runs in seats and background subagents, and nobody waits in a polling loop.
- Each turn the lead checks `date`, `team.sh status` and the repos' recent commits.
- Once a day, prompted by the wiki's crontab, the lead runs `<root>/agentic_workflow/tools/skills-check`, which lists the global skills behind their sources, and asks the operator before updating them (`npx skills update -g`); after an update that changed any, it asks every seat to reload. Tools a skill drives (e.g. reladraw) are not checked.
